# Trackeep Literature 架构定位

接闸：CI `quality-gates / tests` 在测试前执行 `tools/check_map.py --check`；本地收口同样先查。本地证据不代表 GitHub CI 已运行。

## 1. 系统是什么

桌面采集台与 Agent/MCP 是同一条文献管道的两个入口。共享服务 `lit/workflow.py` 保存计划、检索、题录、复核及全文状态；两个入口只负责输入和展示。原 PowerShell 引擎仍负责题录创建，不另造导入引擎。业务规则唯一正文见 [PubMed检索规范](PubMed检索规范_v1.0_20261003.md)。本轮真实双入口验收进度见 [HANDOFF](../HANDOFF.md)。

## 2. 故障去哪查

- 界面／锁定批次／确认写入：`ui/pages/workflow_page.py`、`ui/main_window.py`；后台线程为 `ui/workers.py`。旧 `harvest_page.py` 是历史组件，不在主窗生产导航。
- 计划、恢复、跨入口状态：`lit/workflow.py` 与 `日志/workflow-runs/<run_id>/run.json`。按同一 run_id 查历史，不以按钮完成推断业务完成。
- PubMed数量、解释、日期或错刊：`lit/pubmed.py`；预置身份正本 `.project/pubmed-journals.json`，额外刊名经 NLM 核验。期刊展示表由 `lit/journals.py` 只读加载 Memex，表行不替代身份验证。
- 题录重复／字段冲突／导入：`lit/metadata_batch.py`、`lit/library.py` 与该批次导入回执；原引擎真路径由 `lit/config.py` 指向。`lit/batch_review.py` 负责读回复核和保留／排除／待核。
- 模型未配置、中文计划或未判定：`lit/deepseek.py`，由 workflow 调用；GUI不自行解释模型结果。
- 本机全文缺失／错父项／重跑：`lit/native_fulltext.py` 做先核重、原生优先、官方补充和本机读回；`lit/native_ui.py` 操作原生界面，`lit/native_pdf.py` 复用公共棚解析。界面无法可靠识别、文件尚未验证都不算成功。旧 `fulltext_batch.py` 是云Storage兼容入口，不是WebDAV本机默认路径。
- MCP协议／插件发现：`lit/mcp_server.py`、`plugins/trackeep-literature/`；`.agents/skills/trackeep-literature/SKILL.md` 仅指向唯一技能正文，不维护第二份业务规则。

## 3. 新功能加在哪

业务规则、状态和门禁加在共享服务及相应领域模块，GUI/MCP只适配。期刊身份、来源域和日期口径扩展须配反例；原生附件写入必须通过读回护栏，不能靠内部API或直接存储写入绕过。新模块与地图更新同次提交。

## 4. 各块怎样协调

`gui.py → WorkflowPage → Workflow.dispatch`；`项目Skill/MCP → literature_dispatch → Workflow.dispatch`。共享服务调用 PubMed、原题录引擎、复核和本机原生全文；记录写到项目日志。GUI和Agent复用相同计数、失败与待核状态。原生自动化仅限本机 Windows，客户端安装能力与真实验收范围单列，不能从模拟测试外推。
